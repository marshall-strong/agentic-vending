# The weekly agent run

`python -m vending.agent` runs the agent once: it starts our MCP server, lets the model call the tools, and records the run.

```
python -m vending.agent            # dry run (the default): write tools are hidden, no write is sent
python -m vending.agent --live     # the real run: the model may call submit_desired_state once
```

- **Halt switch:** if it is on, the run is recorded as `halted`. No model call is made and no tool is called. The switch is checked again before every model request, so turning it on mid-run stops the run at that point. A new database starts halted, so turn it off with `python -m vending.halt off --by <name>` first.
- **Model key:** the client is built from `VENDING_ANTHROPIC_API_KEY` and nothing else (see the README for where the team's key lives). Without it the run is recorded as `failed` before the server starts or any request is sent. `ANTHROPIC_API_KEY` is never read, so a run can't bill whoever is signed in on that machine, and no model key is passed on to the MCP server.
- **Spend:** every model request goes through `vending.harness`. Its worst case is in `model_calls` before it is sent, and the run cap (`model_run_cap_cents`) holds. **A live run is the competition's money:** it also goes in the ledger, under `model_daily_cap_cents`. **A dry run is test spend:** it spends real tokens, but under `model_test_daily_cap_cents` and outside the ledger, so practice runs don't use up the live cap or show in the P&L. `python -m vending.usage` shows both. A dry run's read tools still read from the bridge. Each request asks for prompt caching, because every turn re-sends the whole conversation.
- **A cut-off answer:** the harness lowers a request's `max_tokens` to fit what is left of the caps, so late in an expensive run the final answer can be cut off mid-JSON. That run is recorded as `failed` with a detail that says so. Raise the cap, or use a cheaper model or a lower effort.
- **Rules card:** the system prompt starts with [`docs/agent/rules-card.md`](agent/rules-card.md), read once when the run starts, and tells the model to call `get_project_rules` for details. If the card is missing or empty, the run is recorded as `failed` before the server starts or any model request is sent. The system prompt holds nothing that changes between runs (the time, briefing and notes are in the first message), so it can be read from cache. Note: the container image must include `docs/agent/`.
- **Startup read:** after the halt, rules-card and key checks, code calls `get_briefing` once before the first model request. Its compact Markdown follows the time and mode, before the prior notes, labelled as a trusted startup read with its `computed_at` and `snapshot_id`. It uses the stored ledger, stock, polls and request status without a model call. In a week the wake check flagged (#219), it also carries that wake-up row: why a slot is projected to sell out before Friday's restock and a midweek visit would pay. Source ages remain visible even when the briefing was generated just now. If the read fails, the opening says so and directs the model to the existing pull tools. Its competition figures count only from the ledger opening, like `get_account_balance` and `get_pnl`. It does not replace `get_account_balance` every run, the request check before another order, or preview before submit. See [the startup-read note](agent/startup-read.md).
- **Tools:** the server runs with `VENDING_TOOLS=built`, so the model sees only tools that work. A dry run also hides `submit_desired_state`, `set_price`, `request_catalog_product` and `set_wildcard_slot`. If the model calls submit anyway, it gets "Not sent", and nothing reaches the server.
- **Live runs:** a live run refuses to start while the server has no `submit_desired_state` (#37). It sends only the plan its last `preview_desired_state` accepted, and adds that preview's `expected_plan_hash` itself. It sends at most one submit per run, and any later call gets "already submitted".
- **One retry (#217):** only two replies allow one more submit in the same run, because each proves no byte of the request left: our own `plan_changed` alone (the plan moved since the preview; no `submission` number, because no row was saved), and `status: not_filed` (connecting to the bridge failed). The model must preview again, and submit in a later turn, the plan that new preview accepted, with its hash. A second such reply ends the retries: any later call gets "Not sent". **Nothing else allows another send**: not the planner's other refusals, and never a reply to a POST, even the bridge's documented refusal. When in doubt, the agent never sends twice.
- **Open submissions at the start:** before the startup read, a live run runs `vending.submissions.check` (also `python -m vending.submissions check`). It settles only a row whose POST got the bridge's validated `201` (`created_id`, saved before settling) that was never recorded, after a crash or a database error. It reads `GET /api/v1/purchase-requests/{created_id}`, and only the bridge's documented record of that ID settles the row as `accepted`, unless another submission or a request we recorded already holds the ID. Anything else stays open, a `404` included. Every other open row needs a person, even one whose answer named a request: an answer that wasn't the validated `201` may name a request that isn't this attempt's. The submit tool keeps refusing with `submission_unresolved` until then. The check never sends anything. It records a first `tool_result` step, `check_submissions`, when there was a row to check.
- **Orders blocked:** while a row stays open, the briefing raises `submission_unresolved` ("ORDERS BLOCKED") and the dashboard's attention list says "Orders are blocked" with the command to run. A person finds out whether the bridge filed it (asking the instructors if no request ID is known), then runs `python -m vending.submissions resolve N --request-id ID --by NAME`, or `--not-filed --by NAME`.
- **Notes:** the model's notes from the last finished run are in its opening message, labelled with where they came from. A live run reads only live runs' notes, so a dry run's "would submit" is never taken as done. Notes carry over only from runs that started at or after both the real ledger opening (`ledger.real_opening`) and the moment our slots (the server's assignment) were first read (`slots.assigned_at`, the stored assignment's `first_read_at`). With no real opening (none yet, or only the 11 Nov test one), or no stored assignment, no notes carry over. Why: the assignment was redrawn on 20 Nov and is final for the quarter. A run before the redraw, such as run 2 on 12 Nov, may name slots that aren't ours (#216). The opening is recorded on 29 Nov, after the redraw, but a recovery opening could be backdated, so the assignment's time is checked too.

## What a run records

Each run is one row in `agent_runs`, which the dashboard reads:

| status | when |
|---|---|
| `submitted` | a `submit_desired_state` call succeeded. The `request_id` is stored right away, and the run stays `submitted` whatever stops it afterwards |
| `skipped` | the model chose to skip, or a dry run ended (the detail says whether it would have submitted) |
| `halted` | the halt switch was on |
| `failed` | the model key is missing, a cap was reached, the answer was cut off, it ran out of turns, a submit was refused, it said "submit" on a live run without submitting, or something broke (a refused submit that was retried and accepted is `submitted`). A detail that starts with **SUBMISSION UNRESOLVED** means the bridge may have accepted a request: a person settles it with `python -m vending.submissions resolve` before anyone submits again |

**Every step is recorded too**, in `agent_steps` (migration 014), as it happens: the model's reasoning, any text it wrote, each tool call and each tool result (cut to 4,000 characters). The reasoning is the summary the API returns when asked with `thinking: {display: "summarized"}`; the raw chain of thought is never available. The dashboard shows them under each run as **How it decided**. A step that can't be stored is reported on stderr and the run goes on.

The startup read has its own first `tool_result` step for `get_briefing`, labelled `source: "startup"`, with success or failure and the snapshot reference. It has no model-selected `tool_call` step. The full typed snapshot and rendered text are in the MCP read's `action_log` result.

`plan` is the last plan that previewed OK (with its `plan_hash`), or the plan that was submitted. **It also carries what the dashboard shows beside the plan:** `visit` (`scheduled` or `midweek`), the run's `reason`, and a `reason` on each slot the model said it changed (its final answer lists them as `slot_reasons`). A run that stopped before answering stores the plan without reasons. `team_update` and `notes` come from the model's final answer. `cost_usd` is what the harness spent, estimates included.

## When it runs unattended

The worker (`python -m vending.worker`, the Azure container) can start the agent on a schedule. The code is `vending/agent_schedule.py`. It calls `vending.agent.run`, the same entry point as `python -m vending.agent`, so the halt switch, the caps, the run lease and the records are the same.

**A scheduled run is live only when both settings below say `live`.** Then it is `vending.agent.run(live=True)`, exactly what `python -m vending.agent --live` runs, so every live-run rule above holds. Any other pair is a dry run (the model is offered no write tool, so it can't send a purchase request, a catalog request or a price) or off. [Live scheduled runs](#live-scheduled-runs), below, has the checks a live run passes first and how to turn it on and off.

**It is off by default, twice.** The worker runs the agent only when both of these turn it on:

| Setting | Where | Default | |
|---|---|---|---|
| `AGENT_SCHEDULE_MODE` | the container app's env vars (or `.env`) | unset (off) | `off`, `dry-run` or `live`. Unset, the worker never starts the agent and never writes to `agent_schedule`. Anything else is a dry run (never live, never off), and `/health` and the dashboard show it as a Problem |
| `agent_schedule_mode` | the database's `config` table | no row (off) | `off`, `dry-run` or `live`; anything else is a dry run (never live, never off), and the dashboard shows it as a Problem. The lower of the two settings runs. Read by the statement that claims each scheduled time, and again in the transaction that takes the run lease, with its row locked, before anything is paid for. So a change reaches every replica at once |
| `AGENT_SCHEDULE` | env | `wed 14:00-22:00,thu 12:00-20:00` | Eastern times, comma-separated, as `day HH:MM-HH:MM` (24-hour, no offset): when the run is due, then the latest it may start. The default (Kevin, 23 Nov) is a restock run each Wednesday at 2 PM, so its order is in before Amazon's Wed 23:59 cutoff (#188), and one each Thursday at noon, for a week whose Wednesday didn't send (one per visit) |
| `AGENT_SCHEDULE_FROM` | env | `2026-12-02` | The first Eastern day with runs |

Kevin decided the default times on 23 Nov: the first live order is the Thu 3 Dec 12:00 ET run, for the Fri 4 Dec visit (Wed 2 Dec is before the start, so a dry run). The times follow Eastern wall-clock time through daylight saving. A window the clocks skip in March (`sun 02:30-03:00`) has no valid start that day: it is recorded as `missed`, and its detail says the clocks went forward. A wrong time or first day turns the runs off; the worker goes on, logs why, and the dashboard says a setting is wrong. While the worker can't do its scheduled work (the database is down, or missing a migration), `/health` says why and the dashboard shows it as a Problem; the dashboard also reads the database itself and says when it is missing migrations.

- **Turn it on:** set `AGENT_SCHEDULE_MODE` on the container app, as [`docs/deploy.md`](deploy.md) shows (the worker reads it when it starts, so a new revision is needed), and set the database's setting: `python -m vending.config set agent_schedule_mode dry-run --by <name>`. The value is a bare word, so the same command works in bash, cmd and Windows PowerShell 5.1 (which drops the quotes in `'"dry-run"'`). **Turn it off:** set the database's setting to `off`. That takes effect at the next scheduled time on every replica, an old one left running during a deploy too, and on a time already claimed whose run hasn't started: in the transaction that takes the run lease, the agent reads the setting again with its row locked, and if it is off, nothing runs and the row is `skipped`. It takes its locks first and reads the database's clock after them, so a wait on a lock can't carry a start past its latest start; that same reading is the row's `started_at`. An `off` committed while a run is being started waits until that start is recorded (the row's `started_at`), so it applies from the next time on. Changing only the env var does not reach a replica that is still running. The halt switch stops a run that has already started.
- **One run at a time:** every agent run, by hand or scheduled, holds the run lease from start to end (`vending/run_lease.py`, the one row of `agent_run_lease`). It is a row, not a session lock, so a dropped or killed database connection never frees it. The run renews it every minute, and checks it still holds it before each model request and just before a purchase request is sent. The check that counts is in the harness: in the same transaction that reserves a model request's budget, it renews the lease under its row lock and refuses unless the lease then lasts longer than the request can take. A takeover locks the same row, so the two never interleave. A run that lost it stops there and is `failed`, and reserves and sends nothing. A run that finds it taken is recorded as `skipped` at once, and its detail names the other run. A run that stops renewing (its process died) loses it 10 minutes later, and the next run takes it over and records the old run as failed. A run stops at a 60-minute deadline (`RUN_DEADLINE`) and is recorded as `failed`; its lease can't be renewed past the deadline plus 10 minutes. The harness also checks the deadline after counting a request's tokens and again just before sending it, so nothing is sent past it. A model request already sent ends first: the harness gives it at most 5 minutes by the wall clock (`REQUEST_DEADLINE`; the SDK's own timeout only limits each wait for bytes, so a reply that keeps trickling in would outlast it), and sends it only if the lease, just renewed, lasts past that. A request it gives up on keeps its worst-case cost, and while it may still be going the run doesn't give the lease back, so it expires by itself and no other run's request overlaps it. Each tool call times out after 2 minutes (`TOOL_TIMEOUT`), and each database call of the run after 30 seconds, waiting for a lock included (`DB_TIMEOUT`). So a server or a table that stops answering can't hold the lease. The scheduler's own database calls have the same limit. If a scheduled run still hasn't ended 1 h 15 min after it started, the worker records it as `failed`, lets it go and goes on with the schedule; its loop wakes for that deadline.
- **One run per time:** each time in the schedule gets one row in `agent_schedule` (migration 024), keyed by the time, before the agent starts. A restart, or a second replica, never runs the same time again. A time the database's setting turns off is recorded as `skipped`, with mode `off`.
- **A missed time:** if the worker was down at the time, a restarted worker records it as `missed`. If it comes back before the latest start, it runs late, and the row's detail says how late. Whether a time is due, and whether it is past its latest start, is decided by the database's clock, not the worker's: it is read just before the claim is inserted, and again in the transaction that takes the run lease. So a worker whose clock runs slow or fast never starts a run early or after its latest start: past it, the time is `missed`. If the worker can't start the run's thread, the time is `failed` and the worker goes on. If a worker stopped mid-run, the next one records that time as `failed`. It is never run again.
- **What is recorded:** the row's `mode` is `live` or `dry-run`, what actually ran. Its `outcome` is the run's own ending (`submitted`, live runs only; `skipped`, `halted`, `failed`), or `missed`, or `running` while it goes on, with the `agent_runs` id, and through it the request a live run sent. A dry run never submits, so an agent that says `submitted` on a dry run is recorded as `failed`. A `skipped` or `halted` run is a result, not a success. If the worker can't write the ending, it tries again every minute until it lands. If the agent can't write its own ending to `agent_runs`, it tries 3 more times over about 40 seconds; if that still fails, the dashboard keeps the scheduled run in Needs attention, however old, until `agent_runs` has an ending for it.

**See the runs:** `python -m vending.agent_schedule` prints the settings as that machine reads them, the database's setting, the next time and the latest rows with their details. The dashboard's Needs attention reads the `agent_schedule` table itself, so turning the schedule off never hides a run: each failed, missed or halted run stays there for a week, however many runs came after it, and so does a run still `running` past the deadline. The newest run is always there, however old. If the table can't be read, it says the schedule's status is unavailable. Each scheduled run's line says whether it was a live run or a dry run and what it sent: `Sent: request pr-1 (submission 3).`, `May have sent: submission 4 (unknown)` (a submission saved for that time is still `sending` or `unknown`: a Problem, until a person settles it with `python -m vending.submissions resolve`), or, once it has ended, `Nothing sent.` It reads the request from the run's `agent_runs` row and from the submissions saved for that time (`purchase_submissions.schedule_due`), and the agent names its run on the schedule's row as it starts (`run_lease.attach`), so a run whose ending the worker never recorded still shows what it sent. A run meant to be live that didn't run live (a check made it a dry run, or it never started: stopped at the lease, or the run lease busy) is Check, with the check's own words, and stays in Needs attention, under newer runs too, until a later live run has started. A live time that is waiting on a passing check is Check while it waits (from the worker's `/health`), and a Problem with the cause if it is still blocked at its latest start (`LIVE RUN MISSED`). The worker's `/health` and its home page show its own `AGENT_SCHEDULE_MODE`, whether it has the model key (never the key), the next time and the last run's outcome (never its detail). The run itself is in the dashboard's runs, like any other.

### Midweek runs

The midweek wake check (`MIDWEEK_WAKE=on`, #219) records a wake-up when a slot will sell out before Friday and a paid visit would pay (docs/restock-policy.md, section 2). It also requests a run. The worker's scheduler then runs the agent once for that wake-up. The code is `vending/agent_schedule.py`.

- **Same rules as a weekly run.** Both switches (`AGENT_SCHEDULE_MODE` and `agent_schedule_mode`), the start (never live before Thu 3 Dec 00:00 ET), the halt switch, the run lease, the caps and the checks before a send. With `AGENT_SCHEDULE_MODE` unset or off, nothing runs it.
- **When.** Due when the wake-up was requested. The latest start is midnight ET at the end of that day. Past it, the row is `missed`. A weekly time due at the same moment goes first. The worker looks for a request after each round, so it starts within minutes.
- **One a week.** The wake-ups allow one a week (`midweek_wakeups`), and each wake-up gets one row in `agent_schedule`, with `kind` `midweek` and its `wakeup_id` (migration 037).
- **What it may send.** Only an off-cycle visit: the submit refuses an on-cycle plan from a midweek run (`midweek_on_cycle`). It sends at most one midweek submission a week. A midweek visit doesn't count against the weekly run's one per visit, and the weekly run's doesn't count against it.
- **Its opening** says it was started by the wake check, with the wake-up's reason. If no visit is worth the $25 fee, it submits nothing. That is a valid outcome (`skipped`).
- **Where it shows.** Needs attention ("The midweek live run requested ..."), Runs ("midweek run"), the failure banner when it is missed, and `python -m vending.agent_schedule`.

**The team agrees before anyone sets `live`.** A live scheduled run spends the competition's money and sends a purchase request that no person looks at before it goes. Agree on GitHub first, and say who set it and when.

2. The worker reads these when it starts, so this makes a new revision.
3. The database: `python -m vending.config set agent_schedule_mode live --by <name>`.
4. Check the effective schedule on the active revision. `az containerapp show --name ai-group-2-vend --resource-group data_systems_resource_group --query "properties.template.containers[0].env" -o table` lists the three settings. Then `az containerapp exec --name ai-group-2-vend --resource-group data_systems_resource_group --command sh`, and in it `python -m vending.agent_schedule`: it must say `AGENT_SCHEDULE_MODE here: live, from Wed 02 Dec 2026`, the times `wed 14:00-22:00, thu 12:00-20:00`, `agent_schedule_mode in the database: live`, and no missing migrations. Before 2 Dec its next time is Wed 02 Dec 2:00 PM ET (a dry run: before the start); Thu 03 Dec 12:00 PM ET is the first live one.

**Turn it off** with one command: `python -m vending.config set agent_schedule_mode off --by <name>`. It applies from the next scheduled time on every replica, and to a time already claimed whose run hasn't started, as above. `python -m vending.config set agent_schedule_mode dry-run --by <name>` keeps the runs, as dry runs; a live run already claimed then doesn't start, because its mode was chosen before it took the run lease. To stop a run that has already started, turn the halt switch on (`python -m vending.halt on --by <name>`).

**The checks before a send.** A person checks these before pressing send. A scheduled run checks them itself, by the database's clock, when it claims its time, again in the transaction that takes the run lease, and once more in the submit tool at the send. A check that can clear inside the window (marked *waits*) doesn't spend it: the worker claims nothing and tries again every 5 minutes (`LIVE_RETRY`) until the time's latest start. If it still fails then, the time is `missed`, mode `live`, its detail starts `LIVE RUN MISSED` with the cause, and the dashboard shows it as a Problem. While it waits, the worker's `/health` and the dashboard say why (Check).

| Check | Found at the claim | Found in the lease's transaction |
|---|---|---|
| The competition hasn't started (`vending.start.START`, Thu 3 Dec 00:00 ET) | runs as a dry run; its detail says a scheduled run is never live before the start | doesn't start (`skipped`) |
| A purchase submission is still open (`sending` or `unknown`): ORDERS BLOCKED | first settles what `python -m vending.submissions check` can (a row whose POST got a validated `201`, from the bridge's own answer); anything still open: *waits*, and says to run `python -m vending.submissions resolve` | doesn't start (`skipped`) |
| Our slots can't be read (`vending.slots.our_slots`: nothing stored, or not confirmed since the start), or the worker's hourly `slots check` last confirmed them more than 3 hours ago (`SLOTS_FRESH`) | *waits*; says to check with `python -m vending.slots check` | doesn't start (`skipped`) |
| Another agent run holds the run lease | *waits* (also when the run's own start finds the lease taken: nothing started, so the time goes back to waiting) | |
| A scheduled run already sent a submission for this week's visit (the week turns over on Saturday, after the Friday visit), whatever became of it: a request the bridge rejected still counts | runs as a dry run; its detail names that submission | doesn't start (`skipped`) |
| `agent_schedule_mode` changed from `live` since the claim | | doesn't start (`skipped`) |
| The halt switch is on | the agent records the run as `halted` before any model request | the same |
| `VENDING_ANTHROPIC_API_KEY` isn't set on the worker | the time is `failed` with a detail that starts `MODEL KEY MISSING`, and the agent never starts. `/health` shows `model_key: false`, and the dashboard says so before the time comes | |

**At the send.** The run lease records which scheduled time holds it (`agent_run_lease.schedule_due`, migration 030). The agent passes its own lease token and that time to the MCP server it starts (`VENDING_RUN_LEASE` and `VENDING_SCHEDULE_DUE` in the server's environment; an inherited value is never passed on), and the submission is saved with that time. The submit tool never looks up whichever lease is current: a run whose lease expired or was taken over after it handed the call on is refused (`lease_lost`), never treated as a run by hand. After the attempt is saved, it takes its locks first: the lease's row (`for key share`, so no takeover until the POST is answered), the database switch's row and the schedule's row (`for share`, so an `off` committed meanwhile waits and applies after the send). Only then, once the bridge connection is open and before any byte of the request is written, does it read the database's clock and check: the store cutoffs (every submit, by hand too, so neither a lock wait nor a slow connect carries a plan made at Thursday 23:59 past midnight: `past_cutoff`), its own lease, both switches still `live` (the container's `AGENT_SCHEDULE_MODE`, which the MCP server inherits from the worker, and `agent_schedule_mode`), the schedule's row still a live run going, and every check in the table above. A check that fails there sends nothing: the attempt is settled `not_filed` with why, the agent's submit is refused (`lease_lost`, `schedule_not_live` or `past_cutoff`), and the run ends `failed` with the same words.

**A weekly scheduled run never buys an off-cycle visit.** Its job is the order for Friday's visit, so the submit refuses a plan with `off_cycle: true` from a weekly run (`scheduled_off_cycle`) before anything is saved. A person's run by hand may still send one. A midweek run is the other way round: see [Midweek runs](#midweek-runs).

**One scheduled request per visit.** Weekly runs send at most one submission per week's visit, whatever became of it, a rejected request included. A person who means to send another (after a rejection, say) runs `python -m vending.agent --live` by hand: a run by hand holds no scheduled time, so neither this rule nor the schedule's other checks apply to it, only the live run's own rules.

A run that becomes a dry run says why at the start of its detail (`Run as a dry run, not live: ...`). Everything else is the live run's own rules: only the plan its last preview accepted, at most one submit (#217's retry rules), `submission_unresolved`, the caps, the run lease, and the planner's $53 spendable floor (#188). Nobody watches a scheduled run, so it settles what `python -m vending.submissions check` can settle by itself before it waits on an open submission; a row only a person can settle (no validated `201`) still needs `resolve`.

**The first restock request** (Kevin, 23 Nov). The default schedule's first time is Wed 2 Dec, before the start, so it is a dry run. The first restock request is due 23:59 ET Thu 3 Dec, for the Fri 4 Dec restock, and the first live order is the Thu 3 Dec 12:00 ET run (a test pins it). In a later week, a Thursday time is a dry run if Wednesday's run already sent that week's request (one per visit, above). From Wed 9 Dec on, the Wednesday run is live if both settings say so.

**The first fill (29 Nov) is not a scheduled run.** The fill request for the Mon 30 Nov stocking is sent by hand, before 23:59 ET Sun 29 Nov (#214). The schedule's first day is Wed 2 Dec. Leave `agent_schedule_mode` off until the fill is sent.

A dry run ends `skipped`; one that ends `halted` means the halt switch is on, and still proves the worker started it. `python -m vending.agent_schedule` shows the row and its detail. It is test spend, under `model_test_daily_cap_cents`.
5. Afterwards, turn it off: `python -m vending.config set agent_schedule_mode off --by <name>`, and put the times back: `az containerapp update --name ai-group-2-vend --resource-group data_systems_resource_group --remove-env-vars AGENT_SCHEDULE AGENT_SCHEDULE_FROM`.

## Before the first run

A run reads the database `DATABASE_URL` points at, so each of these is per database:

 - [ ] `python -m vending.db migrate`: the run needs `agent_runs` and `model_calls`.
 - [ ] `python -m vending.halt off --by <name>`: a halted database records the run as `halted` and does nothing else, dry runs included.
 - [ ] `python -m vending.ledger open --amount 600.00 --by <name>`: until then `get_account_balance` and `preview_desired_state` can only tell the model the ledger isn't open. The team database still has the 11 Nov test opening: on 29 Nov, reset it first, as [ledger-reset.md](ledger-reset.md) says.
 - [ ] `VENDING_ANTHROPIC_API_KEY` set in your environment, as the README describes.
 - [ ] The class tailnet, since the read tools reach the bridge.

**The first runs against the real model were made on 11 and 12 Nov**, with `claude-opus-5-5` at `medium` and the run cap raised to $5 for testing: a dry run that cost $0.80 over 8 model calls, a live run that cost $0.40, and a dry run that cost $0.08. None was cut off. The caps below are still placeholders, so set them from what these runs cost (`python -m vending.usage` shows each run). At the placeholder $1 run cap, a run like the first would likely be squeezed in its later turns: each turn reserves its worst case (the whole conversation at the cache-write price plus 16,000 output tokens) before it is sent.
